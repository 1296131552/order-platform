## 1. 功能概述

### 1.1 业务背景

订单可视化平台需要支持用户自主注册和管理员创建用户两种场景：

1. **自主注册**：外部人员（供应商、承运商、客户）通过自主注册申请账号
2. **管理员创建**：内部人员（员工、管理层）由管理员直接创建账号
3. **邀请码注册**：特殊合作伙伴通过邀请码快速注册（自动通过审核）

### 1.2 核心需求

| 需求 | 优先级 | 说明 |
|------|--------|------|
| **双渠道注册** | P0 | 自主注册 + 管理员创建 + 邀请码 |
| **审核机制** | P0 | 自主注册需要审核通过后才能登录 |
| **首次登录改密** | P1 | 管理员创建的用户首次登录强制改密 |
| **邀请码管理** | P2 | 自定义过期时间、使用次数、角色身份 |
| **权限分配** | P0 | 混合模式：角色权限 + 用户直接权限 |

### 2.2 渠道对比

| 维度 | 自主注册 | 管理员创建 | 邀请码注册 |
|------|---------|-----------|-----------|
| **注册方式** | 用户填写表单 | 管理员后台创建 | 输入邀请码 |
| **审核流程** | 需要（PENDING） | 不需要（NONE） | 不需要（NONE） |
| **密码设置** | 用户自设密码 | 管理员设默认密码 | 用户自设密码 |
| **首次登录改密** | ❌ 不需要 | ✅ 强制改密 | ❌ 不需要 |
| **角色分配** | 申请角色（需审核） | 管理员分配 | 邀请码预设角色 |
| **使用场景** | 外部合作伙伴 | 内部员工 | 特殊合作伙伴 |

## 3. 注册流程设计

### 3.1 自主注册流程

```
1. 用户访问注册页面
   ↓
2. 填写注册信息（用户名、邮箱、手机号、密码、申请角色）
   ↓
3. 后端验证：
   - 用户名唯一性
   - 邮箱唯一性
   - 手机号唯一性
   - 密码强度
   ↓
4. 创建用户记录：
   - audit_status = 'PENDING'（待审核）
   - is_first_login = 0（用户已设密码）
   - 角色为空（审核通过后分配）
   ↓
5. 返回："注册成功，请等待管理员审核"
   ↓
6. 管理员审核：
   - 通过：audit_status = 'APPROVED'，分配角色
   - 拒绝：audit_status = 'REJECTED'，填写备注
   ↓
7. 用户登录：
   - PENDING：❌ 提示"账号正在审核中"
   - APPROVED：✅ 正常登录
   - REJECTED：❌ 提示"账号审核未通过"
```

### 3.2 管理员创建流程

```
1. 管理员访问用户管理页面
   ↓
2. 填写用户信息（用户名、邮箱、手机号、角色）
   ↓
3. 设置默认密码（如123456）
   ↓
4. 后端创建用户：
   - audit_status = 'NONE'（无需审核）
   - is_first_login = 1（需要强制改密）
   - 分配指定角色
   ↓
5. 返回："用户创建成功"
   ↓
6. 通知用户（邮件/短信/线下）
   ↓
7. 用户首次登录：
   - 系统检测到 is_first_login = 1
   - 强制跳转到密码修改页面
   - 改密后 is_first_login = 0
```

### 3.3 邀请码注册流程

```
1. 管理员生成邀请码：
   - 设置过期时间
   - 设置使用次数
   - 预设角色身份
   ↓
2. 分发邀请码给合作伙伴
   ↓
3. 合作伙伴访问注册页面
   ↓
4. 输入邀请码 + 填写基本信息
   ↓
5. 后端验证邀请码：
   - 邀请码是否有效
   - 是否过期
   - 是否超过使用次数
   ↓
6. 创建用户：
   - audit_status = 'NONE'（自动通过）
   - is_first_login = 0
   - 自动分配预设角色
   ↓
7. 返回："注册成功，可以直接登录"
```

## 4. 数据库设计

### 4.1 新增字段

```sql
-- t_user 表新增审核相关字段
ALTER TABLE t_user ADD COLUMN is_first_login TINYINT(1) NOT NULL DEFAULT 0 COMMENT '首次登录标记: 0-否, 1-是';
ALTER TABLE t_user ADD COLUMN audit_status VARCHAR(20) NOT NULL DEFAULT 'NONE' COMMENT '审核状态: NONE-无需审核, PENDING-待审核, APPROVED-已通过, REJECTED-已拒绝';
ALTER TABLE t_user ADD COLUMN audit_remark VARCHAR(200) COMMENT '审核备注';
ALTER TABLE t_user ADD COLUMN audit_by BIGINT COMMENT '审核人ID';
ALTER TABLE t_user ADD COLUMN audit_time DATETIME COMMENT '审核时间';
```

### 4.2 唯一索引（并发安全）

```sql
-- 复合唯一索引，支持逻辑删除
ALTER TABLE t_user ADD UNIQUE INDEX uk_username (username, is_deleted);
ALTER TABLE t_user ADD UNIQUE INDEX uk_email (email, is_deleted);
ALTER TABLE t_user ADD UNIQUE INDEX uk_phone (phone, is_deleted);
```

### 4.3 查询优化索引

```sql
-- 复合索引：审核状态 + 创建时间（代替低效的单列索引）
ALTER TABLE t_user ADD INDEX idx_audit_status_created (audit_status, created_at);
```

## 5. 权限管理设计

### 5.1 混合权限模式

**设计原则**：
- **80%权限通过角色分配**：批量管理，提高效率
- **20%权限直接分配给用户**：灵活应对特殊场景

**权限来源**：

```
用户权限 = 角色权限 + 用户直接权限
```

### 5.2 权限类型

#### 5.2.1 角色权限

| 角色 | 权限范围 | 说明 |
|------|---------|------|
| **SUPER_ADMIN** | 所有权限 | 超级管理员 |
| **HR_ADMIN** | 人事管理 | 员工管理、角色分配 |
| **DEPT_ADMIN** | 部门管理 | 部门内用户管理 |
| **SUPPLIER** | 供应商权限 | 订单查询、发运管理 |
| **CARRIER** | 承运商权限 | 发运管理、签收确认 |
| **CUSTOMER** | 客户权限 | 订单查询、签收确认 |

#### 5.2.2 用户直接权限

| 权限 | 字段 | 说明 |
|------|------|------|
| **邀请码生成** | `can_generate_invite_code` | 是否可以生成邀请码 |
| **审核权限** | `can_audit_user` | 是否可以审核用户 |
| **特殊操作** | `special_permissions` | JSON字段，存储特殊权限 |

### 5.3 权限分配审计

```sql
-- 用户权限分配记录表（future）
CREATE TABLE t_user_permission_grant (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL COMMENT '用户ID',
    permission_key VARCHAR(100) NOT NULL COMMENT '权限标识',
    granted_by BIGINT NOT NULL COMMENT '授予人ID',
    granted_at DATETIME NOT NULL COMMENT '授予时间',
    expire_time DATETIME COMMENT '过期时间',
    remark VARCHAR(200) COMMENT '备注',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

## 6. 安全机制

### 6.1 并发安全

**问题**：高并发下可能同时注册相同的用户名/邮箱/手机号

**解决方案**：数据库唯一索引

```sql
-- 复合唯一索引保证并发安全
ALTER TABLE t_user ADD UNIQUE INDEX uk_username (username, is_deleted);
```

**好处**：
- ✅ 数据库级别保证唯一性
- ✅ 应用层无需加锁
- ✅ 支持逻辑删除（`is_deleted=0`）

### 6.2 密码安全

| 措施 | 说明 |
|------|------|
| **BCrypt加密** | 使用BCrypt算法加密存储密码 |
| **密码强度验证** | 8-20位，包含大小写字母、数字、特殊字符 |
| **首次登录改密** | 管理员创建用户强制改密 |
| **密码过期** | 90天过期，提醒修改（P2） |

### 6.3 审核状态控制

```java
// 登录时的审核状态检查
if (user.getAuditStatus().equals("PENDING")) {
    throw new BusinessException(ResponseCode.USER_AUDIT_PENDING);
}
if (user.getAuditStatus().equals("REJECTED")) {
    throw new BusinessException(ResponseCode.USER_AUDIT_REJECTED);
}
// APPROVED/NONE 可以正常登录
```

## 9. 设计决策记录

### 9.1 为什么首次登录标记=0/1而不是根据密码判断？

**决策**：使用显式的 `is_first_login` 字段

**原因**：
- ✅ 明确、可控、易于理解
- ✅ 支持强制改密场景
- ✅ 不依赖密码内容判断（更安全）

**备选方案**：根据密码是否为默认密码（如123456）判断

**拒绝原因**：
- ❌ 默认密码可能被用户主动设置
- ❌ 无法区分是管理员创建还是用户自设

### 9.2 为什么使用复合唯一索引（username, is_deleted）？

**决策**：复合唯一索引支持逻辑删除

**原因**：
- ✅ 支持逻辑删除（`is_deleted=1`的用户可以重名）
- ✅ 数据库级别保证并发安全
- ✅ 应用层无需额外加锁

**备选方案**：单列唯一索引 `UNIQUE (username)`

**拒绝原因**：
- ❌ 逻辑删除后用户名被占用，无法恢复

### 9.3 为什么自主注册用户不需要强制改密？

**决策**：自主注册用户 `is_first_login=0`

**原因**：
- ✅ 用户已自己设置密码，无需改密
- ✅ 提升用户体验，减少步骤

**备选方案**：所有新用户都强制改密

**拒绝原因**：
- ❌ 自主注册用户已经设置了密码，强制改密体验差

## 10. 常见问题

### Q1：自主注册用户可以立即登录吗？

**A**：不可以。自主注册用户的 `audit_status='PENDING'`，需要等待管理员审核通过后才能登录。

### Q2：管理员创建用户为什么需要强制改密？

**A**：因为管理员通常使用默认密码（如123456）创建用户，强制改密可以确保账户安全。

### Q3：如何区分不同注册渠道的用户？

**A**：通过 `audit_status` 和 `is_first_login` 组合判断：
- 自主注册：`audit_status='PENDING'`, `is_first_login=0`
- 管理员创建：`audit_status='NONE'`, `is_first_login=1`
- 邀请码注册：`audit_status='NONE'`, `is_first_login=0`

### Q4：并发注册相同的用户名会怎样？

**A**：数据库唯一索引会保证只有一个请求成功，其他请求会返回友好错误提示："用户名已存在"。

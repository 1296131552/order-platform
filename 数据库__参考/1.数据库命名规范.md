# 数据库命名规范

## 一、基本原则

1. **规范统一**：统一命名、统一类型、统一约束
2. **性能优先**：合理设计索引，避免全表扫描
3. **数据安全**：敏感信息加密，权限最小化
4. **可扩展性**：支持分表分库，预留扩展字段
5. **可维护性**：表结构清晰，注释完整
6. **可读性**：命名清晰，见名知意

---

## 二、表命名规范

### 2.1 表名规则

- **前缀**：统一使用 `t_` 前缀
- **命名方式**：使用下划线分隔（snake_case）
- **命名风格**：全小写字母
- **命名长度**：建议不超过 30 个字符
- **命名语义**：使用有意义的英文单词或缩写，清晰描述表的业务含义

### 2.2 表名示例

**正确示例**：
```sql
t_order                    -- 订单表
t_order_line               -- 订单明细表
t_order_status_log         -- 订单状态日志表
t_shipment                 -- 发运批次表
t_receipt                  -- 签收表
t_customer                 -- 客户表
t_user                     -- 用户表
t_user_role                -- 用户角色关联表
```

**错误示例**：
```sql
order                      -- ❌ 缺少 t_ 前缀
Order                      -- ❌ 使用了大写字母
tOrder                     -- ❌ 使用驼峰命名
t_order_detail_table       -- ❌ 表名过长，table 冗余
```

### 2.3 表名分类

#### 2.3.1 业务表
- 核心业务实体表：`t_order`、`t_shipment`、`t_receipt`
- 业务关联表：`t_order_line`、`t_shipment_item`

#### 2.3.2 系统表
- 用户权限表：`t_user`、`t_role`、`t_permission`
- 配置表：`t_system_config`、`t_dict_config`

#### 2.3.3 日志表
- 操作日志表：`t_operation_log`、`t_audit_log`
- 状态日志表：`t_order_status_log`、`t_shipment_status_log`

#### 2.3.4 关联表
- 多对多关联表：`t_user_role`、`t_role_permission`
- 一对多关联表：通常通过外键关联，不单独建表

## 三、字段命名规范

### 3.1 字段名规则

- **命名方式**：使用下划线分隔（snake_case）
- **命名风格**：全小写字母
- **命名长度**：建议不超过 30 个字符
- **命名语义**：清晰描述字段的业务含义

### 3.2 字段名示例

**正确示例**：
```sql
id                         -- 主键ID
order_id                   -- 订单ID
order_no                   -- 订单号
customer_name              -- 客户名称
created_at                 -- 创建时间
updated_at                 -- 更新时间
is_deleted                 -- 是否删除（布尔类型）
status                     -- 状态
```

**错误示例**：
```sql
ID                         -- ❌ 使用了大写字母
orderId                    -- ❌ 使用驼峰命名
order_no_                  -- ❌ 末尾下划线
order_number_of_customer   -- ❌ 字段名过长
```

### 3.3 常用字段命名

#### 3.3.1 主键字段
- **主键**：统一使用 `id`（BIGINT 类型）
- **外键**：使用 `表名_id` 格式，如 `order_id`、`user_id`

#### 3.3.2 时间字段
- **创建时间**：`created_at`（DATETIME 类型）
- **更新时间**：`updated_at`（DATETIME 类型）
- **删除时间**：`deleted_at`（DATETIME 类型，物理删除时使用）
- **业务时间**：根据业务含义命名，如 `operate_time`、`shipment_time`

#### 3.3.3 操作人字段
- **创建人**：`created_by`（BIGINT 类型，关联用户ID）
- **更新人**：`updated_by`（BIGINT 类型，关联用户ID）
- **操作人**：`operator_id`（BIGINT 类型，关联用户ID）

#### 3.3.4 状态字段
- **状态**：`status`（VARCHAR 或 ENUM 类型）
- **是否删除**：`is_deleted` 或 `deleted`（TINYINT 类型，0-未删除，1-已删除）
- **是否启用**：`is_enabled`（TINYINT 类型，0-禁用，1-启用）

#### 3.3.5 编号字段
- **业务编号**：使用 `_no` 后缀，如 `order_no`、`shipment_no`
- **编码字段**：使用 `_code` 后缀，如 `status_code`、`type_code`

#### 3.3.6 名称字段
- **中文名称**：使用 `_name` 后缀，如 `customer_name`、`product_name`
- **英文名称**：使用 `_name_en` 后缀，如 `product_name_en`

#### 3.3.7 数量金额字段
- **数量**：使用 `_count`、`_quantity`、`_qty` 后缀，如 `order_count`、`quantity`
- **金额**：使用 `_amount`、`_price`、`_cost` 后缀，如 `total_amount`、`unit_price`

#### 3.3.8 描述字段
- **描述**：`description`、`remark`、`note`
- **备注**：`remark`、`comment`、`memo`

### 3.4 字段NOT NULL和默认值规范

#### 3.4.1 基本原则
如果没有特殊的业务理由，一般都建议将字段定义为 `NOT NULL`，并使用合适的默认值代替 NULL。

#### 3.4.2 使用NOT NULL的原因
1. **防止空指针问题**：NOT NULL 可以防止出现空指针问题，减少应用层的空值判断逻辑
2. **节省存储空间**：NULL 值存储需要额外的空间，使用默认值可以节省存储
3. **简化比较运算**：NULL 值会导致比较运算更为复杂，使 SQL 查询逻辑变得复杂
4. **优化器优化**：NULL 值会使优化器难以优化 SQL，影响查询性能
5. **索引性能**：NULL 值有可能会导致索引失效，影响索引的查询效率

#### 3.4.3 默认值选择原则
- **字符串类型**：使用空字符串 `''` 作为默认值
- **数值类型**：使用 `0` 作为默认值（根据业务场景，也可使用其他合理的数值）
- **布尔类型**：使用 `0`（否）或 `1`（是）作为默认值
- **时间类型**：根据业务需求选择，可使用 `CURRENT_TIMESTAMP` 或特定时间
- **枚举类型**：使用枚举的第一个值或业务默认值

#### 3.4.4 默认值注释规范
**必须为所有使用默认值的字段添加注释**，说明：
- 为什么使用该默认值
- 默认值的业务含义
- 特殊情况说明

**正确示例**：
```sql
-- 订单状态:默认空字符串表示初始创建状态,避免使用NULL防止索引失效和简化查询逻辑
`status` VARCHAR(30) NOT NULL DEFAULT '' COMMENT '订单状态',

-- 创建人ID:默认0表示系统创建,避免使用NULL防止空指针问题
`created_by` BIGINT NOT NULL DEFAULT 0 COMMENT '创建人ID:0-系统创建',

-- 是否删除:默认0表示未删除,布尔类型使用0/1而非NULL
`is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '是否删除:0-未删除,1-已删除',
```

**错误示例**：
```sql
-- ❌ 缺少NOT NULL和默认值
`status` VARCHAR(30) COMMENT '订单状态',

-- ❌ 缺少注释说明为什么使用该默认值
`status` VARCHAR(30) NOT NULL DEFAULT '' COMMENT '订单状态',

-- ❌ 使用NULL而非默认值
`created_by` BIGINT NULL DEFAULT NULL COMMENT '创建人ID',
```

#### 3.4.5 特殊情况
以下情况允许使用 NULL：
- 字段具有明确的"未知"或"未设置"业务含义，且必须区分"空值"和"未设置"
- 外键字段在业务上允许不存在关联关系
- 可选的时间字段（如删除时间、完成时间等）
- 扩展字段或预留字段

即使允许使用 NULL，也应尽量使用默认值代替，并**必须添加注释说明**为什么需要使用 NULL。

## 四、索引命名规范

### 4.1 索引名规则

- **主键索引**：使用 `PRIMARY KEY`，无需命名
- **唯一索引**：使用 `uk_` 前缀 + 表名 + 字段名
- **普通索引**：使用 `idx_` 前缀 + 表名 + 字段名
- **全文索引**：使用 `ft_` 前缀 + 表名 + 字段名
- **命名方式**：使用下划线分隔（snake_case）
- **命名长度**：建议不超过 30 个字符

### 4.2 索引名示例

**正确示例**：
```sql
-- 唯一索引
UNIQUE KEY `uk_order_order_no` (`order_no`)
UNIQUE KEY `uk_user_username` (`username`)

-- 普通索引
KEY `idx_order_customer_id` (`customer_id`)
KEY `idx_order_status` (`status`)
KEY `idx_order_created_at` (`created_at`)

-- 联合索引
KEY `idx_order_customer_status` (`customer_id`, `status`)
KEY `idx_order_time` (`order_id`, `operate_time`, `business_node`, `to_status`)
```

**错误示例**：
```sql
KEY `index_order_id`          -- ❌ 使用 index 而非 idx
KEY `idxOrderId`              -- ❌ 使用驼峰命名
KEY `idx_order_customer_id_1`  -- ❌ 使用数字后缀
```

### 4.3 索引命名规范

#### 4.3.1 单字段索引
- 格式：`idx_表名_字段名`
- 示例：`idx_order_status`、`idx_user_email`

#### 4.3.2 多字段索引（联合索引）
- 格式：`idx_表名_字段1_字段2`（按字段重要性排序）
- 示例：`idx_order_customer_status`、`idx_order_time`

#### 4.3.3 唯一索引
- 格式：`uk_表名_字段名`
- 示例：`uk_order_order_no`、`uk_user_username`

## 五、约束命名规范

### 5.1 外键约束

- **命名格式**：`fk_表名_关联表名`
- **示例**：
```sql
CONSTRAINT `fk_order_customer` FOREIGN KEY (`customer_id`) REFERENCES `t_customer` (`id`)
CONSTRAINT `fk_order_line_order` FOREIGN KEY (`order_id`) REFERENCES `t_order` (`id`)
```

### 5.2 检查约束

- **命名格式**：`ck_表名_字段名`
- **示例**：
```sql
CONSTRAINT `ck_order_amount` CHECK (`amount` >= 0)
CONSTRAINT `ck_user_age` CHECK (`age` >= 0 AND `age` <= 150)
```

## 六、视图命名规范

### 6.1 视图名规则

- **前缀**：统一使用 `v_` 前缀
- **命名方式**：使用下划线分隔（snake_case）
- **命名风格**：全小写字母

### 6.2 视图名示例

```sql
v_order_summary            -- 订单汇总视图
v_user_permission          -- 用户权限视图
v_shipment_status          -- 发运状态视图
```

## 七、存储过程和函数命名规范

### 7.1 存储过程命名

- **前缀**：统一使用 `sp_` 前缀
- **命名方式**：使用下划线分隔（snake_case）
- **示例**：
```sql
sp_get_order_by_id
sp_update_order_status
sp_calculate_order_amount
```

### 7.2 函数命名

- **前缀**：统一使用 `fn_` 前缀
- **命名方式**：使用下划线分隔（snake_case）
- **示例**：
```sql
fn_get_order_status_name
fn_calculate_discount
fn_format_order_no
```

## 八、触发器命名规范

### 8.1 触发器命名规则

- **前缀**：统一使用 `trg_` 前缀
- **命名格式**：`trg_表名_操作_时机`
- **操作**：`insert`、`update`、`delete`
- **时机**：`before`、`after`

### 8.2 触发器名示例

```sql
trg_order_before_insert    -- 订单插入前触发器
trg_order_after_update      -- 订单更新后触发器
trg_user_before_delete      -- 用户删除前触发器
```

## 九、数据类型规范

### 9.1 整数类型

- **主键ID**：`BIGINT`（支持自增或雪花算法）
- **外键ID**：`BIGINT`
- **状态码**：`TINYINT` 或 `SMALLINT`
- **数量**：根据业务范围选择 `INT` 或 `BIGINT`
- **布尔值**：`TINYINT`（0-否，1-是）

### 9.2 字符串类型

- **短字符串**（≤50字符）：`VARCHAR(50)`
- **中等字符串**（51-200字符）：`VARCHAR(200)`
- **长字符串**（201-500字符）：`VARCHAR(500)`
- **超长字符串**（>500字符）：`TEXT` 或 `LONGTEXT`
- **固定长度**：使用 `CHAR`，如 `CHAR(10)` 用于固定长度编码

### 9.3 日期时间类型

- **日期**：`DATE`
- **时间**：`TIME`
- **日期时间**：`DATETIME`（精确到秒）
- **日期时间（毫秒）**：`DATETIME(3)`（精确到毫秒）
- **时间戳**：`TIMESTAMP`（自动更新时使用）

### 9.4 数值类型

- **金额**：`DECIMAL(18, 2)`（18位总长度，2位小数）
- **百分比**：`DECIMAL(5, 2)`（如 99.99%）
- **浮点数**：根据精度需求选择 `FLOAT` 或 `DOUBLE`

### 9.5 JSON类型

- **扩展字段**：`JSON`（MySQL 5.7+）
- **数组字段**：`JSON`（存储数组格式）

### 9.6 枚举类型

- **状态枚举**：`ENUM('value1', 'value2', 'value3')`
- **类型枚举**：`ENUM('type1', 'type2', 'type3')`

## 十、注释规范

### 10.1 表注释

- **格式**：使用 `COMMENT` 关键字
- **内容**：说明表的业务含义、用途、注意事项
- **示例**：
```sql
CREATE TABLE `t_order` (
  ...
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci 
COMMENT='订单表:记录销售订单的基本信息,包含订单状态、客户关联、金额等核心数据';
```

### 10.2 字段注释

- **格式**：使用 `COMMENT` 关键字
- **内容**：说明字段的业务含义、取值范围、默认值说明
- **位置**：详细说明放在代码前，COMMENT 中保留简短描述
- **默认值注释**：使用默认值的字段**必须**在注释中说明为什么使用该默认值
- **示例**：
```sql
-- 订单状态:默认空字符串表示初始创建状态,避免使用NULL防止索引失效和简化查询逻辑
-- 枚举值:''(初始创建)、DRAFT(草稿)、EXECUTING(执行中)、COMPLETED(已完成)
-- TODO:此处未使用枚举进行限制,待后续确定后再限制
`status` VARCHAR(30) NOT NULL DEFAULT '' COMMENT '订单状态',

-- 创建人ID:默认0表示系统创建,避免使用NULL防止空指针问题
`created_by` BIGINT NOT NULL DEFAULT 0 COMMENT '创建人ID:0-系统创建',
```

### 10.3 索引注释

- **格式**：使用 `COMMENT` 关键字
- **内容**：说明索引的用途、查询场景
- **示例**：
```sql
-- 支持按订单ID查询状态变更历史,并按业务操作时间排序,同时支持业务节点和状态筛选
KEY `idx_order_time` (`order_id`, `operate_time`, `business_node`, `to_status`) 
COMMENT '订单时间线查询索引',
```

## 十一、公共字段规范

### 11.1 标准公共字段

每张业务表应包含以下公共字段（根据业务需求选择）：

```sql
-- 主键
`id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键ID',

-- 创建信息
`created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) COMMENT '创建时间',
`created_by` BIGINT NOT NULL DEFAULT 0 COMMENT '创建人ID',

-- 更新信息
`updated_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) COMMENT '更新时间',
`updated_by` BIGINT NOT NULL DEFAULT 0 COMMENT '更新人ID',

-- 逻辑删除
`is_deleted` TINYINT NOT NULL DEFAULT 0 COMMENT '是否删除:0-未删除,1-已删除',
`deleted_at` DATETIME(3) NULL DEFAULT NULL COMMENT '删除时间',
```

### 11.2 公共字段说明

- **id**：主键，统一使用 BIGINT，支持自增或雪花算法
- **created_at**：创建时间，精确到毫秒，自动设置
- **created_by**：创建人ID，关联用户表
- **updated_at**：更新时间，精确到毫秒，自动更新
- **updated_by**：更新人ID，关联用户表
- **is_deleted**：逻辑删除标记，0-未删除，1-已删除
- **deleted_at**：删除时间，物理删除时使用

## 十四、注意事项

1. **一致性**：在整个项目中保持命名风格的一致性
2. **可读性**：命名要清晰，见名知意，避免使用缩写（除非是通用缩写）
3. **长度限制**：注意数据库对标识符长度的限制（MySQL 默认 64 字符）
4. **保留字**：避免使用数据库保留字作为标识符
5. **版本兼容**：考虑不同数据库版本的兼容性（如 JSON 类型需要 MySQL 5.7+）
6. **注释完整**：重要表和字段必须添加注释，便于维护和理解
7. **NOT NULL优先**：尽可能使用 `NOT NULL` 和合适的默认值，避免使用 NULL，并在注释中说明使用默认值的原因

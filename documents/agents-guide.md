## 1. change-logger — 变更日志记录器

### 核心职责
在**任何代码修改前**必须调用的强制检查点，负责记录所有代码变更历史。

### 主要功能
- 记录变更时间戳、文件路径、变更类型
- 详细的变更描述（修改了什么、为什么修改）
- 影响范围与破坏性变更警告
- 关联需求或任务编号

### 日志格式
```markdown
## [YYYY-MM-DD HH:mm:ss] - [变更类型] - [简要摘要]

**修改文件:**
- `path/to/file1.ts`: 修改说明

**变更类型:** [新增/修改/删除/重构/修复/优化/其他]

**详细描述:**
[详细的中文说明]

**影响范围:**
- [影响的模块/组件]
- [是否是破坏性变更]

**相关需求:**
- [需求文档或任务编号]
```

### 日志存储位置
`memory-back/changeLog.md`

### 触发场景
- 用户请求修改任何代码文件
- 主动建议的 Bug 修复
- 数据库结构变更
- 重构操作

### 变更分类
| 分类 | 说明 |
|------|------|
| 新增 (NEW) | 新文件、新功能 |
| 修改 (MODIFY) | 现有代码的修改 |
| 删除 (DELETE) | 删除文件或功能 |
| 重构 (REFACTOR) | 结构性调整，行为不变 |
| 修复 (FIX) | Bug 修复 |
| 优化 (OPTIMIZE) | 性能优化 |
| 其他 (OTHER) | 文档、配置等 |

## 2. code-commit-architect — 代码提交架构师

### 核心职责
在 Git 提交前分析代码变更，更新项目进度文档和架构文档。

### 主要功能
1. **分析未提交的 Git 变更**
   - 识别新增、修改、删除、移动的文件
   - 理解变更的业务与技术意义

2. **更新 progress.md**
   - 记录完成内容、技术要点
   - 说明影响范围和下一步计划

3. **更新 architecture.md**
   - 文档化新文件的职责与架构位置
   - 说明关键依赖和设计决策
   - 维护模块依赖关系图

### 输出结构
```markdown
## [日期] - [功能/模块名称]

### 完成内容
- [具体变更1]
- [具体变更2]

### 技术要点
- [关键技术决策]

### 影响范围
- 修改文件：[文件列表]
- 影响模块：[模块名称]

### 下一步
- [后续工作]
```

### 触发场景
- 用户完成一个功能模块后准备提交
- 重构完成后需要文档化
- 主动建议：完成任何逻辑代码块后

### 特殊关注点
- DDD 聚合根边界是否被遵守
- 状态机变更是否被记录
- 事件溯源模式是否正确应用

## 3. code-context-bridge — 代码上下文桥接器

### 核心职责
将用户的**高层/模糊需求**转化为**具体实施计划**，是需求意图与技术实现之间的桥梁。

### 主要功能

1. **深度代码库分析**
   - 阅读技术架构文档
   - 搜索相关模块和现有模式
   - 识别聚合根、领域边界

2. **需求澄清与扩展**
   - 提取隐含需求
   - 识别缺失的技术细节
   - 将用户概念映射到项目术语

3. **架构对齐**
   - 确保符合 DDD 原则
   - 尊重聚合根边界
   - 遵循状态机驱动方法

4. **具体实施方案**
   - 提供文件路径和模块位置
   - 定义数据结构和 API 规范
   - 说明数据库变更

### 输出结构
```markdown
**需求理解**
- 用户请求内容
- 实际需要的（隐含需求）
- 识别的技术缺口

**现有代码分析**
- 相关模块和聚合根
- 应遵循的现有模式
- 将被修改的代码位置

**技术方案**
- 详细实施步骤
- 文件结构变更
- API 规范
- 数据库变更

**实现要点**
- 关键技术决策
- 架构对齐理由
- 风险缓解策略

**后续行动**
- 具体实施任务
- 依赖关系
- 测试策略
```

### 触发场景
- 用户描述功能但未指定实现细节
- "我想给订单列表加个筛选功能"
- "发货批次需要能追踪位置"
- "首页要显示一些关键指标"

### 质量自检清单
- [ ] 是否尊重聚合根边界？
- [ ] 是否正确应用事件溯源？
- [ ] 状态转换是否由状态机处理？
- [ ] 是否遵循项目命名规范？
- [ ] 可以先作为 MVP 实现吗？

## 4. git-change-reviewer — Git 变更审查器

### 核心职责
以 **Linus Torvalds** 的视角审查未提交的代码变更，关注代码品味、简洁性和潜在问题。

### 审查哲学

| 原则 | 说明 |
|------|------|
| **Good Taste** | 消除特殊情况，而不是添加 if/else |
| **Never Break Userspace** | 向后兼容是铁律 |
| **Pragmatism** | 解决真实问题，非假想威胁 |
| **Simplicity** | 超过3层缩进就是设计错误 |

### 五层分析框架

```
第0层：三个 Linus 问题
├── 这是真实问题还是想象出来的？
├── 有更简单的方法吗？
└── 会破坏什么吗？

第1层：数据结构分析
└── "糟糕的程序员担心代码，优秀的程序员担心数据结构"

第2层：特殊情况检测
└── 找出所有 if/else 分支，识别设计补丁

第3层：复杂度审查
└── 本质是什么？概念能减半吗？

第4层：破坏性变更分析
└── 列出所有受影响的现有功能

第5层：实用性验证
└── 问题在生产中真实存在吗？
```

### 输出格式
```markdown
【核心判断】
✅ 值得提交: [理由] / ❌ 需要修改: [理由]

【关键洞察】
- 数据结构: [最关键的数据关系]
- 复杂度: [可以消除的复杂度]
- 风险点: [最大的破坏风险]

【Linus式建议】
如果值得提交:
1. 第一步永远是简化数据结构
2. 消除所有特殊情况
3. 以最愚蠢但最清晰的方式实现
4. 确保零破坏性变更
```

### 红旗警告
- 超过3层缩进
- 函数超过30行
- 多重嵌套 if/else
- 复杂布尔逻辑
- 魔术数字
- 复制粘贴的代码块

### 触发场景
- 用户完成新功能实现后
- 多文件修改后的 sanity check
- 主动：重大代码变更后
- 推送到远程前的最终审查

## 5. local-code-reviewer — 本地代码审查器

### 核心职责
对**具体代码片段**进行深入的三层分析，提供架构级别的反馈。

### 三层分析框架

| 层次 | 关注点 | 内容 |
|------|--------|------|
| **现象层** | 立即问题 | 语法错误、资源泄漏、异常处理、边界条件、性能反模式、安全漏洞 |
| **本质层** | 结构问题 | 单一职责违反、代码冗余、耦合问题、状态管理、抽象泄漏 |
| **哲学层** | 设计原则 | Good Taste、简洁性、务实性、命名清晰、数据流单向 |

### 代码气味检测

| 气味 | 说明 |
|------|------|
| **僵化** | 小改动引发大面积修改 |
| **冗余** | 重复逻辑应被提取 |
| **循环依赖** | 模块边界不清 |
| **脆弱性** | 修改破坏不相关功能 |
| **晦涩性** | 意图不清晰 |
| **数据泥团** | 字段应封装成对象 |
| **过度工程** | 为假想场景设计抽象 |

### 输出格式
```markdown
### 1. 快速评估
- 总体评分: ⭐⭐⭐⭐☆ (4/5)
- 一句话总结代码质量

### 2. 关键问题（必须修复）
- **[严重性]** 问题描述
  - 位置: 具体行/函数
  - 为什么有问题
  - 具体修复方案

### 3. 代码气味与设计问题
- **[气味类型]** 描述
  - 当前问题
  - 建议的重构方法

### 4. 项目标准对齐
- 聚合根边界: ✅/⚠️/❌
- 状态机使用: ✅/⚠️/❌
- 命名规范: ✅/⚠️/❌
- 事务管理: ✅/⚠️/❌

### 5. 亮点
- 设计好的部分
- 值得复制的模式

### 6. 重构建议
- **快速见效**: 立即改善的变更
- **架构建议**: 如有正当理由的大型重构
- **未来考虑**: 扩展点
```

### 触发场景
- 用户实现新功能后
- 审查用户粘贴的代码片段
- 检查特定文件的代码气味
- 主动：逻辑代码块完成后

## 6. unit-test-writer — 单元测试编写器

### 核心职责
为代码编写全面的单元测试，确保代码可靠性和防止回归。

### 测试覆盖要求
- 行覆盖率 > 80%
- 分支覆盖率 > 90%
- 测试所有公共方法、边界条件、错误场景

### 测试场景
| 类别 | 内容 |
|------|------|
| **正常路径** | 预期输入的正常操作 |
| **边界条件** | null、空值、最小/最大值 |
| **异常场景** | 各种错误情况 |
| **状态转换** | 有状态组件的状态变化 |
| **集成点** | 数据库、外部服务 |

### AAA 测试模式
```java
@Test
void should_returnOrder_when_givenValidId() {
    // Arrange - 准备测试数据
    Long orderId = 1L;
    when(repository.findById(orderId)).thenReturn(Optional.of(mockOrder));

    // Act - 执行被测方法
    Order result = service.getOrder(orderId);

    // Assert - 验证结果
    assertThat(result).isNotNull();
    assertThat(result.getId()).isEqualTo(orderId);
}
```

### 测试分类
| 类型 | 说明 |
|------|------|
| **单元测试** | 单类隔离测试，使用 mock |
| **集成测试** | 数据库和组件交互测试 |
| **服务层测试** | 业务逻辑验证，repository mock |
| **控制器层测试** | API 端点验证，service mock |

### 测试命名规范
```
should_[ExpectedBehavior]_when_[StateUnderTest]
```

示例：
- `should_returnOrder_when_givenValidId`
- `should_throwException_when_orderNotFound`
- `should_updateStatus_when_transitionValid`

### 触发场景
- 用户实现新服务类后
- 完成功能实现后需要测试覆盖
- 主动：观察到代码编写但缺少测试

### 测试哲学
> 测试是预期行为的文档
> 失败的测试应清楚指示什么坏了
> 优先测试防止关键业务逻辑错误

## 智能体对比矩阵

| 智能体 | 触发时机 | 输入 | 输出 | 必需性 |
|--------|----------|------|------|--------|
| change-logger | 任何代码修改前 | 变更描述 | changeLog.md 条目 | 强制 |
| code-commit-architect | Git 提交前 | Git diff | progress.md + architecture.md | 推荐 |
| code-context-bridge | 需求模糊时 | 用户需求 | 实施方案 | 按需 |
| git-change-reviewer | 代码变更后 | Git diff | Linus 风格审查 | 推荐 |
| local-code-reviewer | 代码编写后 | 文件/代码片段 | 三层分析 | 推荐 |
| unit-test-writer | 代码完成后 | 类/方法 | 单元测试 | 推荐 |

## 最佳实践

### 1. 开发工作流
```
需求 → code-context-bridge → 实现 → local-code-reviewer
→ unit-test-writer → git-change-reviewer → code-commit-architect → 提交
```

### 2. 智能体协作
- `change-logger` 是所有变更的**入口守卫**
- `code-context-bridge` 确保实施与架构对齐
- `local-code-reviewer` 保证代码质量
- `git-change-reviewer` 提供最终把关
- `code-commit-architect` 维护项目记忆

### 3. 何时使用哪个智能体

| 场景 | 使用智能体 |
|------|-----------|
| "我想加个功能"（未说明细节） | code-context-bridge |
| 准备修改任何文件 | change-logger |
| 写完代码想检查质量 | local-code-reviewer |
| 写完代码没写测试 | unit-test-writer |
| 准备提交代码 | git-change-reviewer + code-commit-architect |
